# 下一轮：引导时序、镜像发布与 Root 部署（讨论中）

本文件记录下一轮需求、已确认的发行方向和待选方案；未实现的功能不代表已经完成验收。

## 已确认的发行方向

- 正式产品保留免 Root 一体版和 Root chroot 版。
- 外部 Termux 免 Root PRoot 路线退出正式发行列表，暂保留代码作为开发、调试和迁移入口。

## 新提议：免 Root APK 与桌面内容分开发行

用户提出参考“安装独立 APK → App 内引导下载并载入镜像”的体验，并要求支持断点续传。本轮先讨论，尚未实施。

推荐方案是一个精简 APK 管理内嵌 X11、PRoot、下载和桌面入口；首次点击“安装桌面”后自动下载匹配的桌面与浏览器运行时、校验、部署，再等待桌面就绪后显示引导。同一 APK 保留本地离线包导入，不增加第三条正式产品路线。

- 断点需保存到磁盘，支持网络中断、进程退出、重新打开或设备重启后继续；可暂停、继续和取消，后台显示真实下载进度。
- 固定资源版本、兼容范围和完整性信息；续传时确认仍为同一内容，拒绝拼接不同版本或错误响应。
- 初装前计算压缩包、解压内容和暂存空间；先校验下载，再暂存安装，所有必要步骤成功后才登记完成。失败保留可重试状态，不覆盖已有个人环境。
- 日常 APK 更新继续保留已有容器和个人数据，不因更新 App 自动重导入系统。
- 首次总下载量仍包含桌面和浏览器；主要改善 APK 安装/更新体积、下载恢复和首次操作流程。

源码核对：现有壳 APK 已有 SAF 本地导入，但无 URL 镜像下载、持久下载任务或 HTTP Range/ETag 恢复。现有导入进度为时间估算，无 rootfs 大小/SHA/空间预算校验；安装链需要补返回码检查、暂存与失败恢复。壳 APK 构建仍嵌入 Chromium、Playwright 和 Node，因此仅移除 rootfs 不能得到真正精简的安装器。

## 更新与个人数据：建议规则（尚待实现的部分不作保证）

用户询问后续是否每次拉新镜像、覆盖是否丢历史、是否设置更新源，以及是否停止更新。

- 镜像用于首次安装和明确的重建/大版本迁移；正常发版不触发整个 guest 覆盖。
- APK、本项目桌面/浏览器组件和 Ubuntu 软件包分别维护版本。项目发布清单指向固定、可校验的 Release/下载源；Ubuntu 基础包沿用合适的 APT 源，关键图形与浏览器依赖按验证过的组合受控升级。
- 个人持久数据覆盖聊天/Agent 记忆、凭据与用户配置、浏览器资料、项目和文档；系统更新范围不得包含这些内容。物理独立数据存储和旧用户迁移需要另行实现和验收。
- 用户安装的软件、系统级自定义设置及数据库格式也属于升级迁移范围，不能只复制个人目录就宣称完整迁移。先记录并备份，遇到不兼容改动需有明确处理规则。
- 重大 Ubuntu/目录布局升级先部署独立新环境，备份并迁移数据、自检后再切换；保留可回退的原环境及匹配的数据状态，数据库迁移不可仅靠切回旧系统目录解决。
- 维持一个稳定系统系列、低频重大升级，持续修复与安全维护；锁定配套版本表示经验证后有序推进，不表示永久不更新。

当前已经实现并验收的是 APK 同签名覆盖更新和白名单受管文件同步；个人文件仍和系统位于同一 guest 树内，尚无完整 rootfs 更新器、数据卷分离或 Ubuntu 大版本迁移器。正常 APK 启动不会重新导入已有容器，但现有同名容器重新导入会删除旧 guest，因此该入口应视为重装，不能复用为普通更新。

## 用户已提出的修改

- 首次引导先于桌面出图，黑底和指向尚未出现控件的箭头使人困惑；与下一轮修改一起处理。
- 预期顺序：加载状态 → 桌面出图且目标控件可用 → 新手引导。具体就绪信号待设计。
- 当前 `OmarchyX11Overlay.attachIfNeeded()` 在附加后固定延迟 2200ms 调用引导，未等待桌面及目标控件就绪。

## 已核对的部署现状

- 免 Root 一体 APK 使用内嵌 X11 和 Ubuntu PRoot；stable62 已在 K20 验收。
- 外部 Termux + Termux:X11 + 可选 Deck 支持免 Root PRoot 和 Root chroot。Deck 是悬浮控制工具，不决定 Linux 运行时。
- 两条外部分体路线的 Sway 都运行在 Termux 本机环境，当前使用 `WLR_RENDERER=pixman`；Ubuntu 应用分别进入 PRoot 或 chroot。Root 路线的日常 Chromium 还使用 Termux 侧桥接。
- `install.sh` 的 Root 分支依赖已有可用的 `/data/ubuntu`、Magisk BusyBox 和 Termux 侧依赖；没有下载/导入基础 rootfs 的完整冷安装流程。本轮只做源码核对，没有从零安装或同负载性能对比。
- Root chroot 可避免 Ubuntu 应用的 PRoot 系统调用转换开销；不能把它写成已启用 GPU 加速或固定倍数性能提升。

## 待讨论的交付方向

- 单独发布云端构建的干净 Ubuntu ARM64 桌面 rootfs、校验与构建来源，不发布手机个人环境快照。
- 免 Root 一体版与 Root chroot 版共享桌面核心，分别提供运行时适配和安装验收；名称与发布顺序待讨论。
- Root 路线需要补齐冷安装，再以 K20 同负载测试区分系统调用、文件操作、图形与远端模型等待的影响。
- 独立分区、独立启动的系统是后续独立议题，Root chroot 仍运行在 Android 内核上。
