# 更新职责与下一轮改进清单

日期：2026-11-23。本文整理已确认的维护方向、源码中的缺口与验收要求；待办项尚未实现，不代表已发布的功能。源码核对基线为 `8d42b9212a6673578edbe7969807010e397af254`，此前交付见[在线安装与 K20 验收记录](../reports/online-installer-k20-20261123.md)。

## 已确认的方向

- APK 维护 Android 界面、嵌入式/悬浮操作、输入与显示桥接、内嵌 X11 和 PRoot；沿用持久签名覆盖升级，普通启动不向已有 guest 同步载荷。
- 保留 Ubuntu 官方软件源，由 APT 维护其管理的软件包。项目组件通道补充现有渠道，只管理明确归属本项目的组件，不替换整套 Ubuntu 更新来源。
- 桌面菜单、主题、脚本及 Android 适配功能通过用户显式发起的系统内组件更新交付。第三方应用保留各自支持的更新方式。
- 初装镜像低频汇总已验证的修正，服务新安装；已有用户不跟随镜像重发重新导入系统。镜像版本选择不承担日常功能更新。
- 定制或固定版本的组件需要持续跟进兼容性与安全修复。锁版用于维持经过验证的组合，不表示永久停止维护。
- 不建设完整 rootfs 覆盖更新器、个人数据卷管理器或 Ubuntu 大版本自动迁移器。用户数据继续保存在现有 guest 中，更新组件时保护个人修改。

## 第一优先级：把更新范围与结果做准确

### U1：建立组件清单与文件归属

- [ ] 汇总 APT 软件包、项目脚本、定制图形栈、浏览器配套、第三方应用及其他直接安装组件；记录来源、已安装版本、更新责任、更新方式、依赖和验证状态。
- [ ] 区分项目程序、出厂默认配置、用户覆盖配置、用户数据；登记目前写入 `/usr/local`、`/opt`、`/root/.config` 以及第三方应用启动文件的内容。
- [ ] 保留 Ubuntu 源与用户添加的第三方源；只有确认同名包或文件冲突后才制定局部版本策略，不默认冻结整套 Ubuntu。

验收：每项运行时组件都有维护来源；无法识别的组件明确标为“来源/更新方式待确认”。APT 未管理的组件不会被报告成已随系统全部更新。

### U2：修正现有更新菜单、检查和结果反馈

- [ ] 拆分 Ubuntu 软件更新、项目桌面组件更新、第三方应用更新的职责；尚未接通的入口明确显示状态。
- [ ] 修正[现有更新菜单](../../core/bin/omarchy-menu-ui)中上游 Git 同步与 APT 混合执行的行为。官方 Omarchy 仓库仅作为上游来源，不直接充当 Android 适配版组件发布渠道。
- [ ] 修正[检查脚本](../../core/bin/omarchy-update-check)：分别记录检查结果、时间与失败原因；网络失败、过期的软件包索引及未知组件不能显示为“全部最新”。
- [ ] Git 或 APT 失败后不得继续显示“更新完成”；显示实际变更与失败项目。移除当前升级成功后自动串联的 `autoremove -y`，将清理列为独立操作。

验收：断网、上游异常、APT 索引刷新失败、依赖冲突、部分成功和无需更新都有真实反馈；一个来源失败不掩盖其他来源的结果。检查操作不修改用户的软件源或全局代理。

### U3：保护配置与现有可用组件

- [ ] 明确默认配置与个人修改的加载顺序，组件更新不整目录覆盖 `.config` 或用户主目录。
- [ ] 审核[桌面入口修复脚本](../../core/bin/omarchy-fix-desktops)及其 APT hook 的文件归属和覆盖范围，只修复明确属于本项目的启动适配。
- [ ] 为已有镜像和旧受管文件建立一次性的识别规则；未知文件、个人修改和旧收据保留，不能直接复用初装覆盖脚本。
- [ ] 优先修正 Hermes 安装/重装的候选验证：当前安装器动态取上游包并先解压，[引导修复](../../core/bin/omarchy-repair-hermes-onboarding)却只接受固定版本和源码指纹。应先在暂存环境核对已验证的包与适配，再替换现有程序；未知版本不得先覆盖可用安装再尝试补丁。

验收：在隔离环境加入用户修改后更新，个人桌面配置、浏览器资料、Hermes 模型配置、密钥与历史数据保持不变；文件冲突能说明原因并提供处理路径，不静默覆盖。未知 Hermes 上游包或适配检查失败时保留原可用程序与配置；这项源码风险不表示 K20 已验证的现有安装发生故障。

## 第二优先级：交付最小可用的系统内组件更新

### U4：项目桌面组件包与显式安装入口

- [ ] 第一版采用版本化 `.deb` 桌面组件包，通过本仓 GitHub Release 发布；先覆盖菜单、主题、脚本和启动适配，暂不另建完整 APT 服务。
- [ ] 基于 U1/U3 确定包拥有的文件和依赖，避免与 Ubuntu 软件包争用文件，也不把个人配置直接打成包载荷。
- [ ] 系统菜单提供已安装/可用版本、变更内容、兼容要求和下载校验；更新由用户显式触发，不恢复 APK 启动时的 guest 同步。
- [ ] 下载、安装和检查分阶段显示结果；处理中断、安装失败和旧版本环境，提供组件级恢复或重装路径。不能把该恢复能力表述为整套 Ubuntu 的自动回滚。

验收：已有环境无需重导入镜像即可收到一次真实桌面修正；损坏下载、组件不兼容和安装失败不报告成功，也不改用户数据。不兼容的 APK/运行时组合应有明确提示。

### U5：定制图形栈与浏览器配套的持续维护

- [ ] 为定制图形栈与 Chromium/Playwright/Node 分别建立可追溯的发布单位、来源版本、校验和、依赖与兼容记录。
- [ ] 跟进上游兼容性和安全修复；有适用修复时提供经验证的新组合或补丁，不依靠长期忽略更新。
- [ ] 验证 Ubuntu 共享库更新与定制组件同时使用的情况；只有必要组件采用局部约束，并记录约束原因和解除条件。
- [ ] 浏览器配套升级继续优先在 K20 验证网页、CDP、真实 Agent、下载及截图；图形栈升级验证桌面启动、输入、横竖屏和会话恢复。

验收：普通 Ubuntu 更新与定制组件更新均有独立结果；配套更新保留用户浏览器资料和原 Hermes 模型配置，有明确的旧组合恢复路径。

### U6：第三方应用更新覆盖与入口整合

- [ ] 逐项确认 AI 应用/CLI 是否有可用的上游更新源，哪些需要项目辅助下载与重新应用启动适配；先覆盖已验证、实际支持的应用。
- [ ] 显示各来源的检查时间与状态，将“未安装”“不支持”“检查失败”“被固定版本”与“已最新”区分开。
- [ ] 统一展示 APK、Ubuntu 软件包、项目组件与第三方应用的更新信息；安装仍由各自所属侧执行。

验收：界面能解释组件由谁维护、是否检查成功；某个应用的“安装最新版”脚本不会被当作所有应用的通用更新机制。

### U7：云端构建、发布与 K20 回归

- [ ] 为组件包增加独立云端构建和验证；记录来源提交、组件清单、许可、依赖及真实附件元数据，不要求每次重建镜像或 APK。
- [ ] 补齐组件包涉及的构建输入版本和完整性核验，逐步减少构建时未固定的上游输入。
- [ ] 在隔离环境验证新装、旧版更新、用户修改、网络/安装中断、失败恢复与混合版本；随后在 K20 保留原配置进行真实验收。
- [ ] 保留同签名 APK 升级、guest 关键文件与个人配置保留的回归；公开报告不包含私有模型密钥、用户资料或手机环境快照。

验收：先通过独立构建与隔离验证，再形成 K20 证据并发布；桌面组件与镜像 Release 不抢占 App 的 latest 发布入口。
